# Spring Boot 디버깅

## 작업 흐름

- 먼저 관련 Controller, Service, Security 설정, 예외 처리기, 설정 파일과 기존 `http/*.http` 요청 예제를 읽어 재현 경로를 파악한다. 저장소의 실행 방식과 프로필을 따른다.
- 원인을 좁힐 수 있는 최소한의 입력과 로컬 환경을 사용한다. `.env`나 설정의 비밀값은 읽어 결과에 출력하거나 기록하지 않는다.
- 로컬 서버 실행이 필요하면 프로젝트에 정의된 명령을 사용한다. 이 저장소는 Gradle이므로 기본 실행 예시는 `./gradlew bootRun`이며, 프로필이 필요하면 저장소 지침과 실행 환경을 확인해
  지정한다. 실행 전 기존 서버와 포트 충돌 여부를 확인한다.
- IDE 디버거를 사용할 수 있으면 중단점을 설정해 요청 진입부터 문제 지점까지 확인한다. 별도 원격 디버그 포트는 필요한 경우에만 로컬 바인딩으로 설정하고, 외부 인터페이스에 노출하지 않는다.
- 서버 시작 로그와 요청 처리 로그를 콘솔에서 함께 확인한다. 시작 실패 시 첫 의미 있는 오류와 가장 안쪽의 `Caused by`를 찾고, 요청 실패 시 요청 시각·경로와 스택 트레이스를 연결한다. 후속 예외나
  종료 로그만 보고 원인을 단정하지 않는다.
- 재현 후 관찰된 로그와 응답을 코드 경로에 대조한다. 추정과 확인된 사실을 구분하고, 필요한 경우에만 가장 작은 범위로 수정한다.

## HTTP 요청과 응답 분석

- 기존 `http/*.http` 요청을 우선 재사용해 메서드, 경로, 헤더, 본문 형식을 맞춘다. 동등한 요청은 curl로 보낼 수 있다.
- 우선 로컬 주소 (`http://localhost:<port>`)에 요청한다. 예시:

  ```bash
  curl -i -sS -X GET 'http://localhost:8080/요청경로' \
    -H 'Accept: application/json'
  ```

- POST/PUT 요청은 API 계약과 기존 예제를 확인한 뒤 `Content-Type` 및 JSON 본문을 명시한다. 인증이 필요한 API는 로컬 개발 자격 증명이나 발급받은 토큰을 사용하며, 토큰·비밀번호를
  명령 출력이나 보고서에 남기지 않는다.
- 응답의 HTTP 상태 코드, 헤더, 본문을 함께 살핀다. 2xx/4xx/5xx 상태를 구분하고, 오류 본문이 공통 응답 형식인지 확인한다. 빈 본문, JSON 파싱 실패, 리다이렉트, 지연 및 연결 거부도 구분해
  서버 콘솔과 대조한다.
- 필요하면 `curl -w`로 응답 코드와 총 소요 시간을 관찰한다. 원인 분석을 위해 `-v`를 쓸 때는 Authorization 및 쿠키 등 민감 헤더가 출력되거나 저장되지 않게 한다.
- 로컬 서버 요청도 데이터 변경 가능성을 고려한다. 생성·수정·삭제·파일 업로드·메일 발송·외부 AI 호출처럼 부작용이나 비용이 생기는 경로는 테스트 설정과 대상을 먼저 확인한다. 실제 데이터 변경이나 외부 시스템
  호출이 필요하면 프로젝트 지침에 따라 사용자 승인을 먼저 받는다.

## 결과 공유

- 재현에 사용한 프로필과 요청 (민감값 제거), 관찰한 상태 코드 및 핵심 로그, 확인된 원인과 수정 내용을 간결히 정리한다.
- 전체 로그 덤프나 비밀값 대신 원인 판단에 필요한 최소한의 로그만 인용한다. 검증을 실행했다면 실제 실행 결과만 보고한다.
